### MEGAGLASS-AND-OPT-03: Open the Open with, Send and link-file chooser only when the app is in front and unlocked
- **What**: FileOpener.whenUnlocked waits only for lock.locked == false. AppLock sets the lock only in onStart (or lockNow), so the lock is false while the app is in the background. If the user leaves the app while an 'Open with' or 'Send' download runs, view() or send() calls startActivity(chooser) from the background when the download ends. Android blocks this with no exception, and on return the user finds nothing open. PublicLinkViewModel.openCached is worse: for Purpose.OPEN it calls graph.opener.view(target) directly, with no lock wait. A link-file download that ends while the lock screen shows opens the chooser above the lock. The chooser shows a preview of the file. The FileOpener KDoc says that 'the app chooser must not open over' the lock screen, so this path is a gap in an intended guard.
- **Where**: app/src/main/kotlin/app/megaglass/android/core/FileOpener.kt:95-100 (whenUnlocked, used at lines 72 and 80); app/src/main/kotlin/app/megaglass/android/feature/links/PublicLinkViewModel.kt:458 (openCached)
- **Change**: In whenUnlocked, before `lock.locked.first { !it }`, add `ProcessLifecycleOwner.get().lifecycle.currentStateFlow.first { it.isAtLeast(Lifecycle.State.STARTED) }`. This is the same wait as MegaGlassApp.kt:88-91. The process ON_START runs AppLock.onStart before the coroutine resumes on Main. Thus the lock wait that follows still applies when the app locks on return. Make whenUnlocked non-private (or add `fun viewWhenUnlocked(file: File) = whenUnlocked { view(file) }`), and call it at PublicLinkViewModel.kt:458 in place of graph.opener.view(target).
- **Benefit**: A large file that the user opens with another app, sends, or opens from a link shows its chooser when the user returns (after the unlock). Today this silently does nothing. A link file that finishes while the lock screen shows no longer opens the chooser and its file preview above the lock.
- **Evidence**: AppLock.kt:50-60: onStop only records backgroundSince; onStart sets _locked. FileOpener.kt:72 and 80 call whenUnlocked for COMPLETED OPEN and SHARE items. view() and send() (FileOpener.kt:177-213) call startActivity with FLAG_ACTIVITY_NEW_TASK from the Application context. ReturnGrace.consume (AppLock.kt:237-246) already names the case 'the app was in the background when it tried to start it'. PublicLinkViewModel.kt:453-458: the `done` coroutine calls graph.opener.view(target) with no wait. TransferJobService.kt:96-101: transfers continue in the background. git blame: FileOpener.kt:95-100 from 2eebe91, PublicLinkViewModel.kt:458 from caff632, no 'Report:' commit.
- **Safety**: This is an app-lock change. The changed lines (2eebe91, caff632) are not Report lines, but the change depends on security-review code: AppLock.onStart (AppLock.kt:55-56, 0e1e0da, Report: MEGAGLASS-UX-004) must run before the coroutine resumes on Main. It also moves the time at which expectReturn arms ReturnGrace, a case that 95e6e1e (Report: MEGAGLASS-UX-004) handles by name ('a share started from the background after a download'). ReturnGrace and expectReturn code do not change, and expectReturn still runs just before startActivity. lifecycle-process is already a dependency. No storage, preference or key change.
- **Verify**: Not checked on a device. Emulator: start Open with on a large file, push Home, wait for the end, return. The chooser must show (after the passcode if the timeout passed). Do the same for a file from a public link with lock timeout 'Immediately'. Remaining edge: ProcessLifecycleOwner delays ON_STOP by 700 ms. Thus Android can still block a completion within 700 ms of leaving.
- **Effort**: S. **Risk**: low. **Net lines**: about +3 (estimate).
- **Owner check**: Review this item as an app-lock change (MEGAGLASS-UX-004), not only as a stability fix. Confirm that AppLock.onStart runs before the chooser path resumes, and that the later expectReturn call still gives the grace that 95e6e1e expects.
- **Status**: rejected (owner, 2026-10-30)

### MEGAGLASS-AND-OPT-05: Drop duplicate nodes from paged search results
- **What**: With a limit, NodeRepository.search reads results page by page by offset (keptPages: offset 0, 500, ...). Each page is a separate api.search. The app reads a second page when page 1 had 500 items and some were Rubbish bin matches (scope ALL, no parent). Node changes that arrive between two pages are applied before page 2. When a new node sorts before the offset, the last node of page 1 comes again as the first node of page 2. The typical case is a blank query with a type or date filter (MODIFIED_DESC) while camera uploads or a sync add photos. NodeCollection keys its lazy items by `it.handle`. Thus a duplicate throws IllegalArgumentException ('Key ... was already used') and the app crashes. SearchViewModel searches again 1 s after each burst of node changes, so the race repeats while uploads add nodes.
- **Where**: app/src/main/kotlin/app/megaglass/android/core/mega/NodeRepository.kt:329 (search, final mapping); NodeRepository.kt:71-81 (keptPages); app/src/main/kotlin/app/megaglass/android/ui/components/NodeViews.kt:357,375 (NodeCollection keys); app/src/main/kotlin/app/megaglass/android/feature/search/SearchScreen.kt:134,152 (SearchViewModel)
- **Change**: Line 329: `nodes.distinctBy { it.handle }.map { it.toItem(api) }.sortedFor(order)`. keptPages, the Rubbish bin filter, the limit and the order stay the same.
- **Benefit**: Search no longer crashes when nodes arrive between two result pages. Example: Search with the Images filter and no text, more than 500 matches, some recent photos in the Rubbish bin, while camera uploads run.
- **Evidence**: keptPages (NodeRepository.kt:71-81) appends each page with `items.filterTo(out, keep)` and does not remove duplicates. One `MegaSearchPage.createInstance(offset, limit)` per call (line 324). SearchScreen.kt:152: `order = if (s.query.isBlank()) SortOrder.MODIFIED_DESC`. SearchScreen.kt:134: `graph.nodes.changes.debounce(1000).collect { trigger.update { it + 1 } }`. NodeViews.kt:357/375: `items(items, key = { it.handle })`. Before 5688109 the app read only one page, so the paging brought this race. No device reproduction.
- **Safety**: Touches security-review code: NodeRepository.kt:329 comes from 5688109 (Report: MEGAGLASS-UX-009, a UX item). The change only adds an in-memory de-duplication. It does not simplify, relax or remove the paging, the Rubbish bin filter, the limit or the order (keptPages, lines 71-81). No storage, schema, preference or key change.
- **Verify**: SearchPagesTest covers keptPages but not the SDK call, so a unit test cannot show the race. Verify with a build and an owner live test (many photos, some in the Rubbish bin, camera uploads on, Images filter with no text). Side effect: a de-duplicated full list can have 499 items, so the limit note may not show for that one search.
- **Effort**: S. **Risk**: low. **Net lines**: about 0 (estimate).
- **Owner check**: Confirm the edit of line 329, a line of the MEGAGLASS-UX-009 commit 5688109. The change keeps the paging, the Rubbish bin filter and the limit, and only removes duplicate handles.

## Areas in good shape

- SDK bridge: listeners only emit. Mega.await removes listeners on cancel. `catching` rethrows CancellationException. Getters that take the SDK mutex run on Dispatchers.IO.
- Screen reloads run only while the screen shows (whileObserved, PERF-010). Transfer and camera-upload timers stop when nothing changes (PERF-009).
- Thumbnails: no subcomposition, one shared download per file, the cache trim reads each file once (PERF-002/005/008).
- Camera uploads: 6 h safety net with BATTERY_NOT_LOW, content triggers coalesced 10 s to 2 min. No own wake locks, no exact alarms.
- Transfers: one in-order IO drain, session epochs, guarded job schedule, caught UIJ and setForeground failures.
- Session: serialized with a Mutex, with timeouts and a Retry path. SessionStore uses AtomicFile. The offline store has staging, commit and recovery.
- Viewers: the PDF renderer, ExoPlayer, MediaController and StreamServer are released off the main thread.
- Release build: R8 full mode, shrinkResources, Log.v/d/i stripped, baseline profile, arm64-v8a only, page-aligned libmega.so. The broad keep nz.mega.sdk.** is necessary for SWIG and JNI. The other broad keep (app/proguard-rules.pro:1-5) is not necessary (MEGAGLASS-AND-OPT-09).
- App resources are clean: the app uses all 767 strings and plurals, 160 drawables and all colours (231e030).
- No over-abstraction: no DI framework, no factories. A scan of 646 non-override functions found none without a caller (except the dead members in MEGAGLASS-AND-OPT-10).
- The app uses all runtime dependencies, except the two that MEGAGLASS-AND-OPT-09 removes (compose-material3-adaptive-layout and the sdk core-ktx). WorkManager stays (camera uploads need a dataSync foreground run of up to 5 h).
- Shared empty, loading and error states with Retry (UX-005). Destructive actions ask first or give Undo. Back clears the selection in the main lists. Errors map to user text in one place (UX-008).
- The release artifact app-release.apk is 0.2.5 / versionCode 10, the same as build.gradle.kts, and was built after HEAD 82e41e5. Thus the artifact measurements apply to HEAD.
